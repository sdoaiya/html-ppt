# 模型管理能力设计

> 日期：2026-04-27  
> 主题：为真实资料处理能力补充理解模型与生图模型的设置与状态管理  
> 状态：待用户审阅

## 1. 背景

当前系统已经具备：

- 资料导入
- 工作台预览
- 生图模型配置
- 真实文本类 / 表格类资料处理的基础链路

但随着“真实资料处理能力”进入下一阶段，仅有图片服务配置已经不够。因为系统开始依赖两类不同的模型能力：

1. **理解模型**：用于资料摘要、重点提炼、结构建议
2. **生图模型**：用于页面配图与内容填充图

因此设置页必须从“图片服务设置页”升级为“模型配置与状态管理页”。

---

## 2. 目标

本轮设计的目标是：

> 为系统增加一套最小但清晰的模型管理能力，让理解链路和生图链路都有独立的模型配置入口与状态反馈。

第一阶段只做“双槽模型配置”，不做复杂平台化模型中心。

---

## 3. 范围

### 3.1 本轮纳入范围

1. 一个 **理解模型槽位**
2. 一个 **生图模型槽位**
3. 理解模型支持：
   - OpenAI Compatible
   - OpenRouter
4. 生图模型继续支持 OpenAI Compatible
5. 设置页状态总览
6. 理解链路读取理解模型配置
7. 工作台图片生成读取生图模型配置

### 3.2 本轮不纳入范围

- 多理解模型并存
- 多生图模型并存
- 自动模型路由
- 多模型 fallback
- 模型效果评测
- 模型成本策略

---

## 4. 核心方案比较

### 方案 A：双槽模型配置（推荐）

把设置页拆成两个独立模型槽位：

1. 理解模型
2. 生图模型

优点：

- 结构清晰
- 符合当前系统能力分工
- 易于理解
- 便于后续扩展

风险：

- 还不是完整模型平台

### 方案 B：统一模型中心

设置页做成“模型中心”，统一维护多个模型列表，并由任务层决定使用哪个。

优点：

- 扩展性强

风险：

- 第一阶段过重
- 用户理解成本高
- 不适合当前产品成熟度

### 方案 C：固定厂商优先

第一阶段只做 OpenRouter 理解模型 + OpenAI Compatible 生图模型。

优点：

- 落地快

风险：

- 不够通用
- 后续仍要重构设置结构

## 5. 推荐方案

推荐采用 **方案 A：双槽模型配置**。

核心原则：

> 一个理解模型槽位 + 一个生图模型槽位，分别服务于“内容理解”和“图像生成”。

---

## 6. 设置页信息架构

设置页升级为三部分：

### 6.1 理解模型配置卡

标题：`理解模型`

用途说明：

- 用于资料摘要
- 用于重点提炼
- 用于结构建议

配置字段：

- `provider`
- `baseUrl`
- `apiKey`
- `model`

支持的 provider：

- `openai_compatible`
- `openrouter`

### 6.2 生图模型配置卡

标题：`生图模型`

用途说明：

- 用于工作台配图
- 用于页面内容填充图

配置字段：

- `baseUrl`
- `apiKey`
- `model`

第一阶段维持 OpenAI Compatible 形式。

### 6.3 状态总览卡

用于展示：

- 理解模型是否已配置
- 生图模型是否已配置
- 当前理解模型名称
- 当前生图模型名称
- 最近一次保存状态

---

## 7. 配置对象设计

建议在本地配置层引入两个独立对象：

- `understandingProvider`
- `imageProvider`

### 7.1 understandingProvider

字段建议：

- `provider`
- `baseUrl`
- `apiKey`
- `model`

其中：

- `provider = openai_compatible` 时：
  - 使用用户自定义 `baseUrl`
- `provider = openrouter` 时：
  - 使用 OpenRouter 推荐默认值
  - 同时允许用户调整

### 7.2 imageProvider

沿用当前结构：

- `baseUrl`
- `apiKey`
- `model`
- `responseFormat`

---

## 8. Provider 切换交互

### 8.1 OpenAI Compatible

显示：

- Base URL
- API Key
- Model

### 8.2 OpenRouter

显示：

- API Key
- Model
- Base URL（自动填默认值，但允许改）

这样可以保持表单结构统一，同时对用户明确展示当前 provider 语义。

---

## 9. 页面状态设计

### 9.1 设置页状态

状态卡至少需要表达：

- 理解模型：已配置 / 未配置
- 生图模型：已配置 / 未配置
- 当前模型名
- 最近一次保存结果

### 9.2 工作台状态

工作台右栏需要继续表达：

- 图片服务已连接 / 未配置
- 当前版本保存状态

后续可进一步增加：

- 理解模型当前状态

### 9.3 理解链路状态

当真实资料处理能力继续接通后，应能在理解页或系统层表达：

- 当前正在使用的理解模型
- 当前理解结果是由哪一类 provider 生成

第一阶段不要求复杂监控，只要求状态可感知。

---

## 10. 对现有系统的影响

### 10.1 设置层

从单一图片 provider 设置升级成双 provider 结构。

### 10.2 理解层

理解服务从“规则 + 本地抽取结果”逐步升级为：

- 本地抽取内容块
- 调用理解模型
- 返回结构化理解结果

### 10.3 工作台层

图片生成继续走当前图片 provider，但设置结构会更加清晰：

- 理解模型负责“懂资料”
- 生图模型负责“补图片”

这意味着模型职责正式分层。

---

## 11. 第一阶段最小实现范围

本轮实现不做模型平台化，只做：

1. 一个理解模型配置卡
2. 一个生图模型配置卡
3. 一个状态总览卡
4. 理解模型支持：
   - OpenAI Compatible
   - OpenRouter
5. 生图模型继续支持 OpenAI Compatible

---

## 12. 风险与边界

### 风险 1：用户对 provider 不熟悉

处理方式：

- provider 名称清晰化
- 给默认值和用途说明

### 风险 2：设置过重

处理方式：

- 只保留双槽配置
- 不做模型中心

### 风险 3：理解模型链路未完全接入时，设置先于能力

处理方式：

- 允许先完成设置结构
- 后续逐步让理解页与真实资料处理链路读取该配置

---

## 13. 完成标准

当以下条件满足时，本轮模型管理能力成立：

1. 设置页存在理解模型卡、生图模型卡、状态总览卡
2. 理解模型支持 OpenAI Compatible 与 OpenRouter
3. 生图模型保持现有兼容能力
4. 理解模型与生图模型配置彼此独立
5. 用户可以清楚知道当前哪些模型已配置、当前默认模型是什么

---

## 14. 结论

这轮模型管理能力最适合以“**双槽模型配置**”落地：

- 一个理解模型槽位
- 一个生图模型槽位

这既能支撑真实资料处理能力的下一阶段，也不会把当前系统过早做成复杂的模型平台。
