# 真实资料处理能力设计

> 日期：2026-04-27  
> 主题：从演示资料链路升级到真实文本类与表格类文件处理能力  
> 状态：待用户审阅

## 1. 目标

当前资料生产工作台已经具备可演示的主链路，但资料输入仍然主要依赖演示数据，无法真正建立“用户上传真实资料 → 系统理解 → 结构建议 → 工作台生成”的可信闭环。

本轮设计的目标是：

> 把资料生产系统从“演示型输入”升级为“真实文本类 + 表格类文件输入”的可用链路。

第一阶段聚焦两类真实输入：

- 文本类资料：`txt` / `md` / `docx` / `pdf`
- 表格类资料：`xlsx` / `csv`

同时采用“本地抽取 + LLM 理解”的混合路线：

- 本地负责读取与抽取原始内容
- LLM 负责摘要、重点提炼、结构建议与内容重组建议

---

## 2. 范围

### 2.1 本轮纳入范围

1. 真实文件选择
2. 文本类内容抽取
3. 表格类内容抽取
4. 统一内容块结构
5. 基于内容块的 LLM 理解结果
6. 将理解结果接入理解页、结构页、工作台资料区

### 2.2 本轮不纳入范围

- 扫描版 PDF OCR
- 图片类复杂理解
- 音频转写
- 多人协作
- 所有 Office 格式的复杂保真还原

---

## 3. 核心策略

### 3.1 方案比较

#### 方案 A：纯本地解析

只做本地文件读取与规则分析。

优点：

- 稳定
- 可控
- 低成本

缺点：

- 对摘要、重点提炼、结构建议的质量上限低
- 难以体现系统的智能价值

#### 方案 B：文件直接送 LLM

文件转成模型可接受的内容后，由模型直接负责理解与组织。

优点：

- 理解能力上限更高
- 结构建议更像人类判断

缺点：

- 文件格式边界复杂
- 成本与不确定性更高
- 第一阶段不够稳

#### 方案 C：混合方案（推荐）

采用“两层架构”：

1. 本地抽取层：负责读取文件、清洗与统一结构
2. LLM 理解层：负责摘要、重点提炼、结构建议

优点：

- 本地层稳定
- 模型层只做自己擅长的“理解”
- 易于扩展到更多格式
- 更符合资料生产系统的长期架构

### 3.2 推荐方案

第一阶段采用方案 C：

> 本地抽取内容，统一成内容块，再交给 LLM 做资料理解与结构建议。

---

## 4. 新的数据流

当前数据流：

上传资料 → 演示资料 → 理解页 → 结构页 → 工作台

升级后的数据流：

上传真实资料 → 本地抽取内容 → 统一内容块 → LLM 理解 → 结构建议 → 工作台

新增两个关键层：

1. **文件抽取层**
2. **内容理解层**

这两层之间通过统一内容块结构解耦。

---

## 5. 文件抽取层设计

### 5.1 职责

文件抽取层只负责：

- 判断文件类型
- 读取原始内容
- 提取可用文本 / 表格数据
- 转成统一内容块结构
- 返回抽取状态与错误信息

它不负责：

- 摘要
- 重点提炼
- 结构建议
- 视觉建议

### 5.2 输出结构

建议新增统一数据结构，例如：

- 文件 ID
- 文件名
- 文件类型
- 原始路径
- 抽取状态
- 内容块数组
- 提取摘要
- 抽取错误（如果有）

内容块类型建议包含：

- `heading`
- `paragraph`
- `bullet_list`
- `table`
- `cell_summary`

这样后续理解层只看内容块，不再关心来源是 `pdf`、`docx` 还是 `xlsx`。

### 5.3 文本类抽取目标

对 `txt` / `md` / `docx` / `pdf`：

- 提取正文文本
- 识别段落和标题
- 保留文件内基本顺序
- 输出为 `heading` / `paragraph` / `bullet_list` 结构

第一阶段不要求复杂版式保真，只要求：

> 能把常见业务资料的文本内容稳定抽出来。

### 5.4 表格类抽取目标

对 `xlsx` / `csv`：

- 提取 sheet 名称（如适用）
- 提取表头
- 提取前若干行代表数据
- 生成表格摘要

输出可包含：

- 原始表格块
- 表头列表
- 行列概况
- LLM 后续可理解的简化摘要文本

---

## 6. 内容理解层设计

### 6.1 职责

内容理解层读取“统一内容块”，负责生成：

- 总摘要
- 重点信息
- 冗余判断
- 可视化建议
- 结构建议
- 页面角色建议

它不直接读原始文件。

### 6.2 理解结果

第一阶段理解结果建议包含：

- `summary`
- `keyPoints`
- `duplicates`
- `openQuestions`
- `visualizable`
- `structureHints`

其中：

- `summary`：整体摘要
- `keyPoints`：应被保留的重点
- `duplicates`：可能重复或冗余的内容
- `openQuestions`：仍需用户确认的信息
- `visualizable`：适合转成图表/对比/流程的内容
- `structureHints`：建议页面结构或叙事顺序

### 6.3 LLM 的位置

LLM 不参与文件格式解析，只参与：

- 内容理解
- 重点提炼
- 结构判断
- 表达方式建议

这能减少格式不稳定问题，并保持模型聚焦在“语义理解”上。

---

## 7. 页面改造影响

### 7.1 导入页

从“演示资料页”升级为“真实资料输入页”。

新增/增强内容：

- 已选择文件列表
- 文件类型识别
- 解析状态
- 解析错误提示
- 继续保留目标说明

第一阶段仍可保留演示资料作为 fallback，但默认应优先使用真实文件。

### 7.2 理解页

理解页需展示更真实的信息：

- 每个文件的抽取结果摘要
- 总体摘要
- 重点信息
- 表格发现
- 可视化建议
- 结构建议

目标：

- 让用户相信系统真的“读懂了他的资料”

### 7.3 结构页

结构页不能再只依赖固定模板。应优先使用：

- LLM 给出的结构建议
- 内容块中的重点信息

仍可保留模板化 fallback，但优先级应下降。

### 7.4 工作台

工作台左栏资料区应开始呈现：

- 真实文件
- 真实内容来源
- 抽取状态
- 哪些内容已进入结构与版式生成

这会显著提升可信度。

---

## 8. 推荐实现顺序

### Step 1：真实文件选择链路

- 用户可选真实文件
- 文件列表进项目状态
- 不再强依赖 demo 文件

### Step 2：本地抽取器

- 文本类抽取器
- 表格类抽取器

### Step 3：统一内容块结构

- 抽取结果统一格式
- 项目状态可持有真实抽取结果

### Step 4：LLM 理解层

- 基于内容块生成理解结果
- 输出摘要、重点、结构建议

### Step 5：接入页面链路

- 理解页
- 结构页
- 工作台左栏

---

## 9. 风险与边界

### 风险 1：PDF 抽取质量不稳定

处理方式：

- 第一阶段只承诺“常见文本型 PDF 可用”
- 不承诺扫描版和复杂排版 PDF 的高质量抽取

### 风险 2：表格语义理解复杂

处理方式：

- 先做表头 + 行列摘要
- 复杂业务语义交给 LLM 理解层

### 风险 3：LLM 理解结果不绝对准确

处理方式：

- 所有理解结果都应被视为“建议”
- 页面上要允许用户继续判断与修正

### 风险 4：范围过大

处理方式：

- 第一阶段只做文本类 + 表格类
- 暂不把图片理解、OCR、音频拉进来

---

## 10. 完成标准

当以下条件满足时，可视为第一阶段真实资料处理能力成立：

1. 用户可导入真实文本类与表格类文件
2. 系统能本地抽取原始内容
3. 抽取结果能转成统一内容块结构
4. LLM 可基于内容块生成摘要、重点和结构建议
5. 理解页、结构页、工作台能展示真实数据来源

---

## 11. 结论

第一阶段真实资料处理能力的最优路径是：

> **支持真实文本类 + 表格类文件导入，本地抽取内容，统一为内容块，再交给 LLM 生成理解与结构建议。**

这条路径既稳，又能明显提升系统从“演示原型”到“真实可用工具”的可信度和价值。
